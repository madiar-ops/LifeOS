## 2. Закрыты два дефекта из Фазы 9

### `EnableRetryOnFailure` несовместим с явными транзакциями

**В чём была проблема.** В БД включена стратегия повторов (ADR 19, Neon — облако,
сетевые сбои штатны). EF Core запрещает открывать транзакцию вручную при
активной стратегии: при сбое он повторил бы только упавший вызов, а не всю
транзакцию, и часть изменений применилась бы дважды. Пока это было латентно —
методы `BeginTransactionAsync` / `CommitTransactionAsync` нигде не вызывались.

**Что сделано.** Тройка `Begin/Commit/Rollback` заменена одним методом:

```csharp
await _unitOfWork.ExecuteInTransactionAsync(async ct => {
    // несколько операций
});
```

Внутри — `CreateExecutionStrategy()`, который повторяет операцию **целиком**.
Коммит автоматический при успехе, откат при любом исключении.

### `RefreshToken.IsExpired` обходил `IDateTimeProvider`

**В чём была проблема.** Свойство читало `DateTime.UtcNow` прямо из доменной
сущности. Проверить истечение токена в тесте было невозможно — пришлось бы
ждать семь дней.

**Что сделано.** Свойства заменены методами `IsExpiredAt(utcNow)` и
`IsActiveAt(utcNow)`. Источник времени в приложении остался один.

## 3. Ограничение частоты запросов

Раньше перебор паролей сдерживался только временем работы BCrypt (~0.25 с
на попытку) — это около 14 000 попыток в час с одного адреса.

| Политика | Лимит | Ключ разделения | Где применяется |
|---|---|---|---|
| `auth` | 5 / 5 минут | IP-адрес | `/auth/register`, `/auth/login`, `/auth/refresh` |
| `ai` | 20 / минуту | UserId | все эндпоинты, ходящие в FastAPI |
| `global` | 120 / минуту | UserId или IP | доступна для остального API |

Отказ отдаёт **429** с заголовком `Retry-After` и телом в формате
ProblemDetails с кодом `rate_limit.exceeded` — фронтенд может показать
осмысленное «попробуйте через N секунд».

Лимит на AI отдельный, потому что каждый такой вызов уходит в FastAPI
и может стоить обращения к платному LLM.

## 4. Production-настройки

| Настройка | Зачем |
|---|---|
| `UseForwardedHeaders` **первым** в конвейере | На Render TLS терминируется балансировщиком. Без этого `Request.Scheme` всегда `http`, `RemoteIpAddress` — адрес прокси (ограничение частоты считало бы всех одним клиентом), а `UseHttpsRedirection` ушёл бы в цикл редиректов |
| `UseHsts` только в Production | В разработке заголовок закешировался бы для `localhost` и сломал другие локальные проекты по HTTP |
| Заголовки безопасности | `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy` |
| Serilog: в проде только консоль | ФС на PaaS эфемерна — логи в файл исчезают при рестарте. Платформа собирает stdout |
| `UseRateLimiter` **после** `UseAuthentication` | Лимит для авторизованных считается по UserId, а он появляется только после аутентификации |

## 5. Docker-образы

| Решение | Почему |
|---|---|
| **Многоступенчатая сборка везде** | В финальный образ backend не попадает SDK (≈700 МБ), исходники и NuGet-кэш |
| **Сначала `.csproj`, потом исходники** | Docker кэширует слой `restore`: пока зависимости не менялись, он не выполняется заново |
| **`npm ci`, а не `npm install`** | Ставит строго зафиксированное в lock-файле; сборка воспроизводима |
| **Непривилегированный пользователь во всех образах** | Выполнение кода внутри контейнера не даёт прав root |
| **Модели обучаются НА ЭТАПЕ СБОРКИ образа** | Копировать артефакты нельзя — образ зависел бы от диска разработчика. Обучать при старте нельзя — PaaS убьёт контейнер, не дождавшись ответа на порт. Обучение детерминировано (фиксированный seed), поэтому веса одинаковы везде |
| **Датасеты удаляются после обучения** | Образ меньше на десятки мегабайт; для инференса они не нужны |
| **AI-сервис не публикует порт в compose** | Доступен только backend'у внутри сети — тот же принцип, что в проде |
| **`try_files ... /index.html` в nginx** | React Router обрабатывает маршруты на клиенте. Без этой строки прямой переход на `/goals` или F5 давали бы 404 |
| **`/assets/` кэшируется на год, `index.html` — никогда** | Vite добавляет хеш в имена ассетов. `index.html` с кэшем показывал бы старую версию после деплоя |
| **`VITE_API_BASE_URL` как build-arg** | У Vite нет рантайм-конфигурации: адрес API вшивается в бандл при сборке |

## 6. CI (GitHub Actions)

Четыре задачи, первые три параллельно:

1. **Backend** — restore, build, `dotnet test` (Testcontainers поднимает настоящий PostgreSQL; Docker на `ubuntu-latest` есть из коробки)
2. **Frontend** — `npm ci`, typecheck, lint, `vitest run`, build
3. **AI Service** — установка, **обучение всех моделей**, `pytest`
4. **Docker** — сборка обоих образов (запускается после 1 и 3)

Обучение моделей в CI решает две задачи сразу: проверяет, что скрипты
обучения не сломаны, и готовит артефакты для тестов.

Параллельность важна: падение фронтенда не должно скрывать результат
по backend.

## 7. Развёртывание

### База — Neon

Создать проект → скопировать строку подключения. Обязательно `SSL Mode=Require`.

### Backend и AI — Render (Blueprint)

Dashboard → **New** → **Blueprint** → указать репозиторий. Render прочитает
`render.yaml` и создаст оба сервиса.

`INTERNAL_API_KEY` генерируется автоматически, а backend ссылается на него
через `fromService` — **синхронизировать ключ вручную не нужно**, что снимает
самую частую ошибку развёртывания.

Задать вручную в панели (помечены `sync: false`):

| Сервис | Переменная |
|---|---|
| lifeos-api | `ConnectionStrings__DefaultConnection` |
| lifeos-api | `FileStorage__Bucket`, `FileStorage__CredentialsJson` |
| lifeos-api | `Cors__AllowedOrigins__0` — адрес фронтенда на Vercel |
| lifeos-ai | `LLM_API_KEY` (необязательно) |

### Миграции в проде

Автомиграции работают **только в Development** (ADR 18) — иначе несколько
инстансов гонялись бы за схему. В проде:

```bash
cd backend
dotnet ef database update \
  --project src/LifeOS.Infrastructure \
  --startup-project src/LifeOS.API \
  --connection "<строка подключения Neon>"
```

### Frontend — Vercel

Import Project → Root Directory: `frontend` → добавить переменную
`VITE_API_BASE_URL` с адресом backend на Render.

**После деплоя фронтенда** вернуться в Render и вписать полученный адрес
в `Cors__AllowedOrigins__0`, иначе браузер заблокирует запросы.

## 8. Проверка (чек-лист)

**Локально**
- [ ] `docker compose up --build` поднимает все четыре контейнера
- [ ] http://localhost:3000 открывается, регистрация работает
- [ ] Прямой переход на http://localhost:3000/goals не даёт 404 (проверка nginx)
- [ ] AI-анализ работает (backend видит ai-service по внутреннему имени)
- [ ] `docker compose down && docker compose up -d` — данные пережили рестарт

**Ограничение частоты**
- [ ] Шесть раз подряд неверный логин → шестой ответ **429** с `Retry-After`
- [ ] Через 5 минут вход снова работает

**CI**
- [ ] Push в ветку запускает все четыре задачи
- [ ] Все зелёные

**Production**
- [ ] `GET /api/ping` на Render отвечает 200

- [ ] Фронтенд на Vercel работает с backend на Render (CORS настроен)
- [ ] В ответах присутствуют заголовки безопасности
- [ ] Логи Render показывают Serilog в консоли

## 9. Осознанно отложено

| Задача | Почему не сейчас |
|---|---|
| **Refresh-токен в httpOnly cookie** | Требует правок backend (установка cookie, защита от CSRF, CORS с `credentials`) и переделки уже протестированного слоя сети на фронтенде. Текущая схема безопасна: refresh в localStorage компенсирован ротацией и обнаружением повторного использования (ADR 24, 89) — украденный токен обнаруживается |
| **Admin-модуль** | `AdminController` на backend не реализован. Пункт меню на несуществующий API выглядел бы готовой функцией и падал при первом нажатии (ADR 117). Решение о включении в MVP — за автором |
| **E2E-тесты (Playwright)** | Единственное, что закрывает совместную работу трёх живых сервисов. Кандидат на доработку после защиты |

Отложенное — не забытое: каждый пункт имеет обоснование, которое можно
привести на защите.
