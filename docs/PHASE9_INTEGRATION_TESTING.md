## 1. Что было сделано

Проект получил четыре независимых уровня проверки. Каждый отвечает на свой вопрос
и намеренно не дублирует остальные.

| Уровень | Где | Чем проверяется | Тестов |
|---|---|---|---|
| Unit backend | `backend/tests/LifeOS.UnitTests` | xUnit + NSubstitute + FluentAssertions | ~95 |
| Интеграционный backend | `backend/tests/LifeOS.IntegrationTests` | xUnit + WebApplicationFactory + Testcontainers (настоящий PostgreSQL) | ~50 |

| AI-сервис | `ai-service/tests` | pytest | 164 |

Точные числа тестов backend приведены ориентировочно: часть из них параметризованы
через `[Theory]`, и итоговое количество кейсов зависит от набора `[InlineData]`.
Фактическое число покажет первый прогон `dotnet test`.

## 2. Почему уровни разделены именно так

**Unit-тесты backend не трогают базу.** Сервисы `GoalService`, `TaskService`,
`FinanceService`, `HealthLogService` и `DashboardService` работают через
`IQueryable` и асинхронные операторы EF Core (`ToListAsync`, `Include`,
`GroupBy`). Подделать такой источник данных заглушкой нельзя без собственного
провайдера запросов: тест получился бы сложнее проверяемого кода и проверял бы
самодельный провайдер, а не сервис. Поэтому в unit-тесты вынесено ровно то,
что от БД не зависит:

- `AuthService` и `UserService` — они работают через методы репозитория, а не
  через `IQueryable`, и потому подставляются честно;
- все 15 валидаторов FluentValidation;
- `CrudGuard`, `PaginationParams`, `PagedResult`, `Result`/`Error`;
- `FileValidationRules` (сигнатуры файлов);
- `BCryptPasswordHasher`, `JwtTokenGenerator`;
- профиль AutoMapper;
- `AiEnvelopeExtensions` — перенос уверенности модели в ответ клиенту.

**Логика, завязанная на БД, проверяется интеграционно.** Через настоящий HTTP,
настоящий JWT и настоящий PostgreSQL в контейнере.

**Провайдер EF InMemory сознательно не используется.** Он выполняет LINQ в памяти
и «переваривает» любые выражения, включая те, которые Npgsql перевести в SQL не
смог бы. Самый сложный запрос проекта — агрегаты `DashboardService` на `GroupBy` —
на InMemory прошёл бы всегда, а в проде упал бы. Тест, который не может упасть,
не имеет ценности.

## 3. Как запускать

### Backend

```bash
cd backend
dotnet test                                  # оба тестовых проекта
dotnet test tests/LifeOS.UnitTests           # только unit — быстро, без Docker
dotnet test tests/LifeOS.IntegrationTests    # требует запущенного Docker
```

**Интеграционные тесты требуют работающего Docker Desktop.** Testcontainers сам
поднимает `postgres:16-alpine`, накатывает миграции и гасит контейнер после
прогона. Никакой ручной подготовки БД, строк подключения и секретов не нужно:
всё подставляется в памяти внутри `ApiFixture`.

Если Docker не запущен, прогон падает с сообщением о недоступности docker-демона.
Это ожидаемое поведение, а не поломка тестов.

### Frontend

```bash
cd frontend
npm run test           # разовый прогон
npm run test:coverage  # с покрытием
npm run check          # typecheck + lint + test
```

### AI-сервис

```bash
cd ai-service
pytest -v
```

Тестам нужны обученные модели в `app/ml/artifacts/`. Если их нет, воспроизводятся
командами обучения из `ai-service/README.md` — обучение детерминировано
(фиксированный seed), метрики повторяются до знака.

## 4. Что именно проверяется (Prompt 5 — Integration)

### JWT

- регистрация выдаёт рабочий access-токен; `GET /api/auth/me` его принимает;
- защищённые маршруты **всех десяти модулей** без токена отвечают 401
  (параметризованный тест — забытый `[Authorize]` на новом контроллере
  обнаруживается сразу);
- токен с испорченной подписью → 401;
- мусор вместо токена → 401, а не 500;
- истёкший токен → 401 **с заголовком `X-Token-Expired: true`**;
- токен, подписанный чужим ключом, этого заголовка **не** получает —
  фронтенд по этому различию решает, обновлять токен или разлогинивать;
- `ClockSkew = 0` подтверждён: токен, просроченный на минуту, уже не принимается.

### Ротация refresh-токенов

- обновление выдаёт новый refresh и гасит прежний;
- повторное предъявление погашенного токена → `auth.token_reuse_detected`
  и **отзыв всей цепочки**, включая токен законного клиента;
- выход идемпотентен, повторный выход снова даёт 204.

### CRUD

- полные циклы создания / чтения / изменения / удаления для целей, задач,
  операций и записей здоровья;
- счётчики задач у цели пересчитываются после отметки выполнения;
- удаление цели **сохраняет** её задачи (`ON DELETE SET NULL`) — тест
  подтверждает, что предупреждение в интерфейсе не расходится с поведением сервера;
- фильтры и поиск работают совместно, поиск нечувствителен к регистру;
- размер страницы ограничен сотней, отрицательный номер приводится к первому.

### Изоляция данных (IDOR)

- чужая цель недоступна на чтение, изменение и удаление — **404, а не 403**;
- существующая чужая и вовсе несуществующая цель дают **неотличимый** ответ;
- список целей содержит только свои записи;
- задачу нельзя привязать к чужой цели;
- чужую задачу нельзя отметить выполненной;
- чужой профиль по идентификатору → 403;
- сводка Dashboard не видит данные других пользователей.

### AI

- уверенность, объяснение, вклад признаков и версия модели доходят до клиента
  без потерь (требование MASTER_GUIDE);
- низкая уверенность передаётся как есть и не превращается в ошибку;
- отсутствие данных → 400 с кодом `finance.no_data`, а не 500 —
  интерфейс показывает подсказку, а не сообщение об аварии;
- в AI-сервис уходят только помесячные итоги: описания операций, даты и
  идентификаторы за пределы backend не передаются;
- недоступность AI-сервиса даёт структурированный ответ с `traceId`;
- успешный анализ попадает в аудит `/api/ai/history`.

### Загрузка файлов

Проверяется на уровне unit-тестов `FileValidationRules`: соответствие MIME-типов
модулям, сопоставление расширений, а главное — **сигнатуры первых байтов**.
Отдельно зафиксировано, что переименованный в `.pdf` исполняемый файл Windows
(`MZ`-заголовок) проверку не проходит, а обрезанный до двух байтов PDF не
«проскакивает» из-за нехватки данных для сравнения.

Сквозная загрузка через HTTP в интеграционные тесты не вынесена сознательно:
она потребовала бы либо Firebase, либо записи в файловую систему тестового
хоста. Правила приёма при этом уже покрыты, а сам провайдер хранилища
переключается конфигурацией.

### Ошибки и валидация

- ошибки валидации приходят словарём «поле → сообщения» (`ValidationProblemDetails`);
- несколько нарушенных правил возвращаются одним ответом;
- несуществующее значение enum → 400, а не 500 (ошибка привязки модели
  перехватывается `ValidationFilter`);
- битый JSON → 400;
- некорректный GUID в маршруте → 404;
- в каждой ошибке есть `code` и `traceId`;
- ответ приходит с типом `application/problem+json`.

### Схема БД

- непринятых миграций не осталось;
- к каждой из 13 таблиц выполняется настоящий SQL-запрос со всеми колонками
  модели — забытая миграция даёт `undefined_column` и валит тест;
- `/health` подтверждает связь с PostgreSQL.

## 5. Пределы проверки (что НЕ покрыто и почему)

Честный список важнее красивой цифры покрытия.

1. **Firebase Storage.** Тесты работают с локальным провайдером (`ForceLocal`).
   Настоящая загрузка в Firebase требует боевого бакета и ключа сервисного
   аккаунта; в CI это секрет, который нельзя коммитить. Абстракция
   `IFileStorageService` проверена, конкретная реализация — нет.
2. **Живой FastAPI из backend-тестов.** Контракт AI-сервиса проверяется его
   собственными 164 тестами, стык — заглушкой. Совместная работа двух
   запущенных сервисов проверяется вручную по чек-листу §7.
3. **Настоящий вызов LLM.** Ветка с языковой моделью в ai-service покрыта
   подменой клиента; фактические HTTP-заголовки и таймауты к внешнему API
   не проверялись.
4. **Модули Study и Career на уровне HTTP.** Их сценарии требуют настоящего PDF
   в хранилище и извлечения текста; покрыты валидаторы и логика AI-сервиса.
5. **Страницы фронтенда и графики.** Recharts в jsdom не вычисляет размеры
   контейнера и рисует пустой SVG; тест проверял бы заглушку `ResizeObserver`.
   Страницы потребовали бы поднимать провайдеры и мокать по 5–10 сервисов на
   экран — это территория e2e, а не unit. Визуально все 11 экранов проверены
   в Фазе 8 прогоном в headless-браузере.
6. **Нагрузка и параллелизм.** Поведение под одновременными запросами
   (в частности, гонка двух регистраций на один email, которую страхует
   уникальный индекс) не измерялось.

## 6. Найденные дефекты

### 6.1 Исправлено в этой фазе (ai-service)

**Сбой проверки внутреннего ключа при не-ASCII значении** — `app/security.py`.
`hmac.compare_digest` отказывается сравнивать строки с не-ASCII символами и
бросал `TypeError`. Запрос с ключом на кириллице получал **500 вместо 401**,
а сервис писал в лог необработанное исключение по чужому запросу — это и
замусоривание логов, и различимый отклик для зондирования.
Исправлено сравнением байтов. Регрессионный тест:
`tests/test_security.py::test_non_ascii_key_is_rejected_not_crashed`.

**Молчаливо пустой конспект** — `app/utils/text_utils.py`, `app/services/study_service.py`.
Фильтр «предложение короче 25 символов — мусор» на конспекте из коротких тезисов
отбрасывал весь текст, и `/study/summary` отдавал 200 с пустым `summary` и
обычной уверенностью 0.465 — то есть пустоту под видом нормального ответа.
Исправлено откатом к неотфильтрованным предложениям, а при действительно
непригодном материале — ответом с `confidence = 0` и прямым объяснением
причины, как требует MASTER_GUIDE.

### 6.2 Замечания без правки кода

**Латентный конфликт стратегии повторов и явных транзакций.** В
`AddInfrastructure` включён `EnableRetryOnFailure`, а `IUnitOfWork` предоставляет
`BeginTransactionAsync`/`CommitTransactionAsync`. EF Core запрещает
использовать явную транзакцию вместе со стратегией повторов: попытка бросит
`InvalidOperationException` с требованием обернуть работу в
`CreateExecutionStrategy().ExecuteAsync(...)`. Сейчас **ни один сервис этими
методами не пользуется**, поэтому дефекта нет — но первый же вызов в будущем
упадёт в рантайме, а не на компиляции. Рекомендация: либо удалить неиспользуемые
методы из интерфейса, либо сразу обернуть их реализацию в execution strategy.

**`RefreshToken.IsExpired` сравнивается с `DateTime.UtcNow` напрямую**, минуя
`IDateTimeProvider`. Абстракция времени, введённая в Фазе 1 ради тестируемости,
в этой точке обходится: проверить истечение токена «сдвигом часов» нельзя,
тест вынужден задавать заведомо прошедшую дату. Не ошибка, но непоследовательность.

**Чтение заголовка `X-Token-Expired` на фронтенде идёт по нижнему регистру
через индексатор** (`headers['x-token-expired']`). Это опирается на деталь
реализации axios (он приводит имена заголовков ответа к нижнему регистру).
`AxiosHeaders.get('x-token-expired')` было бы устойчивее. Поведение при промахе
безопасное — попытка обновления токена, — поэтому правка не вносилась.

## 7. Чек-лист ручной сквозной проверки

Автотесты не заменяют один прогон живой системы. Порядок запуска:

1. `docker compose up -d` — PostgreSQL.
2. `cd ai-service && uvicorn app.main:app --port 8000` — проверить `GET /ping`.
3. `cd backend && dotnet run --project src/LifeOS.API` — проверить Swagger и `/api/ping`.
4. `cd frontend && npm run dev` — открыть страницу **Настройки → Связь с API**.

Затем пройти сценарий и отметить результат:

- [ ] Регистрация нового пользователя, автоматический вход
- [ ] Пустой Dashboard показывает нули и подсказки, а не ошибки
- [ ] Создание цели → создание задачи в ней → отметка выполнения
- [ ] Прогресс цели и Dashboard обновились без перезагрузки страницы
- [ ] Добавление дохода и расхода, корректная сводка и круговая диаграмма
- [ ] Запись здоровья; повторная запись за тот же день даёт понятное сообщение
- [ ] Загрузка PDF в модуль «Учёба», конспект, генерация и прохождение теста
- [ ] Загрузка резюме в «Карьеру», разбор, отображение уверенности модели
- [ ] AI-анализ финансов и здоровья: показаны confidence и вклад признаков
- [ ] Остановить ai-service → повторить анализ → интерфейс сообщает о недоступности AI, а не падает
- [ ] Оставить вкладку на 15+ минут → действие в интерфейсе проходит без разлогина (сработал refresh)
- [ ] Смена пароля завершает все сессии
- [ ] Тёмная и светлая темы, узкий экран (мобильная ширина)

## 8. Предложения по улучшению (Prompt 6)

По убыванию отношения пользы к трудозатратам.

1. **Убрать `EnableRetryOnFailure` либо обернуть транзакции в execution strategy** —
   см. §6.2. Полчаса работы, снимает мину замедленного действия.
2. **Ограничение частоты запросов на `/api/auth/login` и `/api/auth/register`.**
   Сейчас перебор паролей ограничен только временем работы BCrypt (~0.25 с
   на попытку). Встроенный `RateLimiter` из ASP.NET 8 закрывает это десятком
   строк в `Program.cs`.
3. **Refresh-токен в httpOnly-cookie** вместо `localStorage`. Уже записано
   в открытые вопросы как кандидат на Фазу 10: снимает целый класс XSS-атак
   на угон сессии.
4. **GitHub Actions**: `dotnet test` + `npm run check` + `pytest` на каждый push.
   Docker в раннерах GitHub есть, поэтому Testcontainers заработает без правок.
5. **Заголовки безопасности** (`X-Content-Type-Options`, `Referrer-Policy`,
   `Content-Security-Policy`) — одно middleware, заметный эффект на аудите.
6. **Админ-модуль.** `AdminController` на бэкенде не реализован, и раздела нет
   в интерфейсе. Решение о включении в MVP всё ещё открыто.
7. **Тесты сквозного сценария (Playwright)** поверх запущенной связки трёх
   сервисов — единственное, что закрывает пункт 2 из §5.
